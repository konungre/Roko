# Offline signed release admission

`verify_release.py` authenticates release bytes using a provisioned Ed25519 public
key and a trusted minimum sequence. It never extracts an archive, installs an
image, writes a boot entry, changes the rollback floor, or starts a service.

The detached metadata is canonical JSON using `release.canonical`, with exactly:

```json
{"bytes":123,"release":"example-1","schema":"roko-signed-release-v1","sequence":1,"sha256":"<64 lowercase hex digits>"}
```

Replace the example size and digest with the completed release archive's exact
size and SHA256. The signature is Ed25519 over the bytes
`ROKO-OFFLINE-RELEASE-V1\n` followed by the canonical JSON (including its final
newline). The metadata contains no algorithm selector or key URL.
A signing system must keep its private key separate from the delivered bundle.
Only temporary test keys are generated by the tests; none are release trust keys.

```sh
python3 distro/verify_release.py release.tar release.json release.sig trusted-public.pem --minimum-sequence 1
```

The trusted public key and minimum sequence must be supplied by trusted
provisioning and protected storage. Taking them from the download would defeat
signature and rollback checks. Equal sequence values are accepted for repeat
admission; an installation controller must bind the accepted sequence to a digest
and define its replay/recovery policy. Future key rotation needs an authenticated
transition; this gate does not invent one.

The gate rejects noncanonical or duplicate JSON, noninteger sequence/size values,
wrong key algorithms, bad signatures, linked/nonregular files, size mismatches,
changed file metadata, and incorrect payload hashes. It bounds reads and invokes
a trusted `/usr/bin/openssl` without a shell. A successful receipt describes
observed bytes; it is not a capability to reopen a mutable path later. An updater
must hold/protect the admitted artifact or reverify immediately before use.

Remaining production work: signed release policy and key provisioning, protected
monotonic rollback storage, A/B installation, boot-attempt accounting, successful
boot confirmation, known-good fallback, recovery media, and interruption tests at
every durable write boundary. Firmware Secure Boot is a separate trust chain.

Validation uses real OpenSSL-generated Ed25519 keys/signatures, modified payloads,
wrong keys, altered signed metadata, stale sequences, linked files, and a full
`release.pack` to signed-admission path. Payload fixtures are deliberately small;
these tests do not claim a signed production OS exists.

## Interruption-safe staging checkpoint

`stage_release.py` runs only as an unprivileged user. It authenticates the source,
checks disk headroom, creates a new private output directory, copies bounded
inputs, authenticates the actual copy, then publishes `bundle.tar` and `READY`
with file and directory fsyncs. Neither a slot nor a boot entry is selected.

```sh
mkdir -m 700 /tmp/roko-staging
python3 distro/stage_release.py release.tar release.json release.sig trusted-public.pem /tmp/roko-staging/attempt-1 --minimum-sequence 1
```

A failure leaves its new directory for inspection. The same directory cannot be
reused, adopted or overwritten. `inspect(directory, trusted_public_key, floor)`
returns `incomplete` without READY; with READY it authenticates the payload and
metadata again using the current external rollback floor. READY contents never
grant authorization. Use a fresh directory for a separately authorized retry.
The source/copy digest, sequence, release ID and trust key identity must agree.

Tests inject failure after directory sync, metadata sync, payload sync, copied
signature verification, payload publication, receipt sync, and final READY sync.
A subprocess actually exits at the payload-published boundary; recovery observes
an incomplete directory and no boot selection. Additional tests cover source
mutation, corrupted staged data, updated rollback floors, unavailable space,
root execution and public staging parents. These establish process-interruption
behavior on the host filesystem, not physical power-loss guarantees, device
cache behavior, bootloader rollback, or an A/B update implementation.

A separate [userspace boot-trial journal](update/README.md) now consumes verified
staging metadata and tests bounded trial/fallback behavior. It deliberately does
not install a payload or change actual boot selection. Production slot and firmware
integration remains open.
